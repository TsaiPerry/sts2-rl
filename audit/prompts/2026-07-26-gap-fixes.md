## Why this one cannot run beside the others

Every audit record hashes the sim files it audited. **Editing `sts2_rl/` makes
those records stale** — that is the staleness detector working as designed,
and it already fired once on this branch when `main` moved underneath it. A
fix stream running concurrently with the audit streams would invalidate
records as fast as they are written, and an invalidated record needs an agent
re-audit, not a script.

So: run the audit tiers to completion first, then fixes in **one** stream,

## Per-gap procedure

1. **Find the pin.** Most gaps have a `strict=True` xfail in
   `test/test_hook_order.py`. That test is the specification: it already
   asserts the game's behaviour and currently fails for the recorded reason.
2. **Confirm it fails for that reason** before changing anything
   (`py -m pytest <path>::<test> -q --runxfail`).
3. **Fix the engine.** Smallest change that makes the game's behaviour true.
4. **Remove the `xfail` decorator.** A gap fixed with the marker left on
   XPASSes, and `strict=True` turns that into a failure — so the suite tells
   you if you forget. Do not "fix" a strict XPASS by loosening the marker.
5. **Run the covering tests, then the full suite.** Fixes in this codebase
   have wide blast radius; the queue names it per entry.
6. **Re-audit the affected records.** Your edit changed a hashed sim file, so
   `py tools/audit_status.py` will show those records stale. Re-audit each —
   confirm the fixed entry is now `faithful`, and check the rest of the record
   still holds against the changed code. **Regenerating the hash without
   re-reading is the one thing that silently destroys this pipeline's value.**
7. **Commit** the engine change, the test change, and the updated record
   together.

## Grouped fixes

Several queue entries are one mechanism recorded at several sites, carrying
the same verdict at each. The queue marks these. Fix the mechanism once,
clear every pin in the group in the same commit, and update every record that
carried it — leaving one site fixed and its twin recorded as a gap
reintroduces exactly the cross-record inconsistency that this project's rule 3
exists to catch.

## The conformance seeds are your regression net

Beyond the unit suite, this project has recorded conformance seeds that replay
real runs. A fix that greens a pin but desyncs a seed is not a fix. After each
group, run the conformance check and report the delta. Several queued gaps are
expected to **improve** seed convergence — if one does, say by how much; that
is the headline result this whole pipeline was built to produce.

## When a fix recipe turns out to be wrong

The recipes were written by an aggregating agent from a record, not by
someone who tried them. If a recipe does not survive contact with the code:
stop, re-derive the correct fix from the C# source and the record's evidence,
and **report the discrepancy** so the queue can be corrected. Do not
improvise a fix that makes the pin pass without matching the game.
