Round 10 closed Tier 1 and left this as the named next step. The headline "0

## Why "unlabelled" is not a third state

It is a hole. An unlabelled entry inherits its mechanism's liveness in the
queue's arithmetic, which is why `counts` can report 0 live and 646 "in a dormant
mech" at the same time — the inheritance is a display convenience, not a finding.
The shared contract asks for the typed `live` key precisely so this cannot recur.

## Scope decided by Perry, 2026-07-29

1. **Wave 1 — label, in parallel, records only.** Settle each entry as STALE /
   DORMANT+enumeration / LIVE. No `sts2_rl/**` or `test/**` edits, because a
   single engine edit stales every record that hashed that file and concurrent
   fix agents would invalidate records as fast as the triage agents write them.
2. **Wave 2 — fix the LIVE residue, serially**, with engine code, failing-first
   tests, record re-audit and a suite run, as rounds 6–10 did.
3. **Depth: every entry settled by execution.** A dormancy *argument* is worth
   much less than a dormancy *enumeration*; several past dormancy labels were
   correct only by accident, resting on a false premise about the sim or the
   source.

### The one thing the partition cannot make disjoint

Five mechanisms have sites in more than one batch:

| mechanism | batches holding sites |
|---|---|
| `power/_stack_type_single` | power-1, power-2, power-3, power-5 |
| `power_cmd/G5` | power-1, power-2, power-3, seam-power-cmd |
| `power/_death_prevention_branch` | power-2, power-3, power-4 |
| `damage_pipeline/G2` | seam-damage-turn, seam-power-cmd |
| `damage_pipeline/G3` | relic-1, relic-2, relic-5 |

Per-site **liveness** may legitimately differ — one site reachable, its twin not.
Per-mechanism **verdict** may not (binding rule 3). So every agent holding a
shared-mechanism site labels its own site by execution, and routes any
`gap → faithful` flip on such an entry to `HANDOFF` instead of taking it
unilaterally. The controller reconciles those flips across batches before the
wave closes. Leaving one site fixed and its twin recorded as a gap is exactly the
cross-record inconsistency rule 3 exists to catch.

## Definition of done, wave 1

1. `gap_queue.py counts` reports **0 unlabelled**.
2. Every entry that stayed a gap carries a typed `live` key.
3. Every `live: false` carries an enumeration, not an argument.
4. Every `live: true` carries divergence / observable / trigger / fix / radius.
5. `harness.py validate` clean on every touched record; `audit_status.py` shows

6. `harness.py rehash --all` run **once**, by the controller, at the end — never
   by a batch agent, and never without the re-read that earns it.
7. `GAP-QUEUE.md` regenerated; `cite-check` and `coverage` exit 0.
8. Suite at or above the baseline below.

## Expected shape of the result

The one worked slice ran 4 stale / 4 real. Staleness has been the largest
category eight rounds running, at roughly one entry in four. If a batch comes
back with no staleness and no inconclusives, that is a signal to re-read it, not
a clean bill of health — the failure mode this pipeline keeps producing is the
**false clear**, the direction nothing downstream re-checks.
